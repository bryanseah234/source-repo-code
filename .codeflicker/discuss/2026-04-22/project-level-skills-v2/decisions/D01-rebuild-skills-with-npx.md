# 放弃现有手写 skills，改用 npx skills 生态重建

**决策时间**：#R5
**状态**：✅ 已确认
**关联大纲**：[返回大纲](../outline.md)

---

## 📋 背景

### 问题/需求
当前 sourcerepo 中已有一批手写的 `.github/skills/*.md` 文件，但这些文件并不是通过 `npx skills` 工具安装得到的，用户担心它们不符合当前 skills 生态的规范来源与目录约定。用户希望让 Skills 作为可传播资产，在 sourcerepo 中建立后，再同步到所有当前和未来仓库。

### 约束条件
- 需要兼顾多个 IDE / 编码代理，而不是只针对单一工具。
- 需要与现有 GitHub Actions 同步机制配合。
- 用户希望未来可以持续扩展，而不是一次性手工维护。
- `npx skills add` 是正式安装入口，用户希望以其生态为准。

---

## 🎯 目标

建立一个基于 `npx skills` 生态的 Skills 管理方式，使 sourcerepo 成为统一的 skills 源头，并可将安装结果同步到所有项目仓库。

---

## 📊 方案对比

| 方案 | 描述 | 优势 | 劣势 | 决策 |
|------|------|------|------|------|
| A | 继续保留当前手写 `.github/skills/*.md` | 不需要迁移，短期成本低 | 来源不规范，和 `npx skills` 生态脱节，跨代理兼容性弱 | ❌ |
| B | 删除旧 skills，重新用 `npx skills add` 安装所需 skills | 来源规范，可复用公开生态，可持续更新 | 需要重新挑选 skill 源并调整目录/同步方式 | ✅ |
| C | 每个目标仓库单独运行 `npx skills add` | 每个仓库都“原地安装”，语义直接 | 工作流复杂、执行成本高、失败点多，不利于统一治理 | ❌ |

---

## ✅ 最终决策

### 选定方案
删除当前不规范的手写 skills 资产，重新选择公开 skills 仓库，并通过 `npx skills add` 在 sourcerepo 中安装，再将安装后的结果同步到所有目标仓库。

### 决策理由
- 能对齐 `npx skills` 的标准安装与目录结构。
- sourcerepo 仍然可以作为传播中心，不需要每个项目重复执行安装命令。
- 更容易扩展到多代理、多 IDE。
- 后续更新 strategy 更清晰：更新 sourcerepo 中的已安装 skills，再同步出去。

### 预期效果
- 所有仓库中的 skills 来源清晰且一致。
- 未来新增 skill 时，只需在源仓库中安装并触发同步。
- 跨代理兼容性比现有手写模式更强。

---

## ❌ 被否决的方案

### 继续沿用旧手写 skills
- **否决原因**：与 `npx skills` 生态脱节，难以确认兼容性与发现路径，长期维护成本高。
- **重新考虑条件**：如果未来确认某些自定义 skills 无法通过 `npx skills` 管理，才考虑保留少量手写自定义补充。

### 每个仓库各自安装
- **否决原因**：重复执行、失败风险高、CI 复杂度上升，不适合作为统一治理方案。
- **重新考虑条件**：若某些 agent 必须本地执行安装且不能通过文件传播解决，可对个别仓库例外处理。
